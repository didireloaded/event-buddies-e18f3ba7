## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

## Project rules

- Use a feature branch and pull request for new changes. Run `npm run check` before requesting review. GitHub Actions repeats the checks using the committed Bun lockfile.
- `VITE_` settings are public browser configuration. Keep privileged credentials server-side. `npm run build` includes the client-secret format check. Follow the launch gates in `docs/engineering/launch-readiness.md`.

- For attendee UI, copy, design reviews and builder prompts, read `docs/skills/anti-slop-brutal/SKILL.md` and its supplied manual. Apply alongside `docs/skills/strict-interface-engineer/SKILL.md`. The manual’s six-part format applies to design reviews.
- Preserve truthful local-only state while the backend connection is deferred. Social context, timestamps, ETAs and retention claims must match implemented behaviour.
- For future connected crew work, read `docs/engineering/cloud-integration-brief.md`. It reconciles the supplied backend/toolkit prompts with current code, invite authorisation, ownership, expiring shares and offline replay. Recheck provider documentation before implementation.

- Event data lives only in `src/lib/event/sound-of-summer.ts`; UI derives everything from `getDemoData()` so no fabricated times, GPS or counts appear.
- Attendee navigation uses Events, Lineup, Map and Crew. Profile is available in the header. Keep hash routes (`#home`, `#lineup`, `#map`, `#crew`, `#you`, `#info`, `#events`) so Back and deep links retain their meaning.
- Local demo state goes through `useAttendee` (localStorage, key scoped by event id); never claim sync.
- Service worker is generated by vite-plugin-pwa into `.output/public` and registered only from `src/lib/pwa.ts`, because preview/dev must never run a SW.
- The latest owner direction is monochrome UI with real event photos, a glass-card event picker, a published-event calendar and a charcoal venue map. Follow `docs/design/discovery-and-monochrome.md` and the supplied visual references. Historical pink/paper proposals are retained as sources. Use the tokens and `ios-*` classes in `src/styles.css`.
- Keep bottom navigation hidden through onboarding and event selection. It appears only after the attendee confirms an event. Preserve reduced-motion behavior and crew-plan import deep links.
- All backend work is deferred by the owner. Preserve the current integration boundaries. `docs/product/source-register.md` indexes all supplied text attachments and `docs/product/requirements-ledger.md` tracks the 220 numbered feature ideas, including partial and deferred work.
- `docs/` contains supplied references and archived proposals. The skills explicitly linked above are active project guidance. Verify proposals against current code before describing them as implemented.
